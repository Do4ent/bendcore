# Участие в разработке bendcore

bendcore — ядро CAD на C++20 поверх Open CASCADE (OCCT) и интерфейс на React/TypeScript,
работающий с ядром через WebAssembly. Лицензия — MIT (`LICENSE`); присылая изменения, вы
соглашаетесь распространять их на тех же условиях. Зависимости должны быть совместимы с
MIT: GPL-библиотеки (например, LibreDWG, SolveSpace, Gmsh) не подключаются
(`docs/ROADMAP_GENERAL_CAD.md`, разделы 2.5 и 3).

## С чего начать

1. `README.md` — что есть в репозитории, сборка и тесты.
2. `docs/PROJECT_PROCESS.md` — регламент: роли, правило «никаких заглушек», критерии
   готовности задачи (Definition of Done), владение файлами, ветки.
3. `docs/ROADMAP_GENERAL_CAD.md` — план до v1.0; `docs/V1_READINESS.md` — что из него
   выполнено и что блокирует выпуск.
4. Документация модуля, который вы меняете: `docs/kernel/`, `docs/modeling/`,
   `docs/assembly/`, `docs/drawing/`, `docs/ui/`, `docs/qa/`.

## Сборка и тесты

Требования: CMake ≥ 3.20, Ninja, компилятор C++20, Eigen ≥ 3.3, Node.js ≥ 18; для ядра — OCCT
8.0.1 с проверками (`docs/kernel/OCCT_BUILD.md`). Команды — `README.md`, раздел «Сборка и
тесты»; WASM — `docs/WASM_BUILD_GUIDE.md` и `docs/ui/*.md`; трубный модуль — `docs/TESTING.md`.

Перед отправкой изменений:

```bash
ctest --test-dir build-occt --output-on-failure          # native с OCCT
npm run typecheck && npx jest                             # TypeScript
bash scripts/check_no_stubs.sh --diff ccr-d188a25e-rml7z8 # правило «никаких заглушек»
```

и сквозные тесты Playwright страниц, которых касается изменение (`npm run test:e2e:<набор>`).

## Требования к изменениям

- **Без заглушек** (`docs/PROJECT_PROCESS.md`, раздел 2): неподдерживаемый случай — явная
  ошибка с причиной и запись в разделе «Ограничения» документации модуля. Нарушение
  `check_no_stubs.sh` блокирует слияние.
- **Тесты против независимого эталона**: аналитика, известная геометрия, значения сторонней
  CAD — а не значение, которое возвращает сам код.
- **Данные стандартов** (ГОСТ, ISO, EN), записанные без официального издания, помечаются
  «требует сверки» и вносятся в `docs/STANDARDS_VERIFICATION.md`.
- **Документация** обновляется в том же изменении: модульный документ (назначение, API,
  алгоритм, ограничения, как тестировать) и, если меняется поведение интерфейса,
  `docs/USER_GUIDE/`. Документируется только то, что есть в коде и проверено тестом.
- Не создавайте отчётов о «завершении» этапов: результат фиксируется тестами, документом
  модуля и записью в `docs/PROJECT_LOG.md` при приёмке (`docs/DOCS_CLEANUP.md`).
- Новые модули подключаются своим `cmake/<модуль>.cmake`; корневой `CMakeLists.txt` и
  `.github/workflows/` меняются только по согласованию (`docs/PROJECT_PROCESS.md`, раздел 5).

## Коммиты и ветки

Коммиты небольшие, сообщение объясняет «зачем». Работа ведётся в отдельной ветке;
интеграционная ветка — `ccr-d188a25e-rml7z8`, слияние после проверки сборки, тестов,
`check_no_stubs.sh` и документации (`docs/PROJECT_PROCESS.md`, раздел 6).

## Сообщение об ошибке

Укажите: ревизию (`git rev-parse HEAD`), конфигурацию (native/WASM, браузер), шаги
воспроизведения, ожидаемый и фактический результат, файл модели, если ошибка связана с
геометрией. Для ошибок загрузки файлов — вход, на котором воспроизводится
(`docs/qa/QA.md`, раздел 7: `fuzz_replay`).
