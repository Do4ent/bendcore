Каждый замер — `timed(тест, шаг, порог, …)` из `stress_util.hpp`: печатает строку
`[stress] <UTC> <тест> <шаг> <с> (limit …) peakRSS …` и дописывает строку JSON с меткой времени в
`BENDCORE_STRESS_REPORT` (ctest: `build-occt/stress-report.jsonl`):

```json
{"time":"2026-11-11T16:26:06Z","test":"part_300","step":"rebuild_after_sketch_edit","seconds":63.705,"limit_seconds":180.0,"peak_rss_mib":188}
```

Порог умножается на `BENDCORE_STRESS_TIME_SCALE` (CI: 1,5). Пороги заданы с запасом 2–3× к
базовой линии (раздел 2), чтобы ловить деградацию в разы, а не шум машины.

## 3. Профилирование и оптимизация (фаза 5, 2026-11-12)

Профиль — выборка стеков главного потока через `gdb` раз в 0,5–1 с во время теста (`perf` в
контейнере нет); доля — процент выборок, в стеке которых есть функция.

### Деталь из 300 операций (`part_300`)

Профиль до (60 выборок, перестроение после изменения первого эскиза): сама булева операция
(`BOPAlgo_PaveFiller` + построитель) — **≈ 5–10 %**; остальное — проверки и интегралы по всему
растущему телу: `BRepAlgoAPI_Check` входа (самопересечения, `BOPAlgo_CheckerSI`) — 30 %,
`BRepCheck_Analyzer` (вход выдавливания, вход `applyTool`, результат `applyTool`, результат
ядра дважды, результат документа) — 27 %, `BRepGProp` объём/площадь (ядро: аргумент и результат
дважды; моделирование: объём до/после выреза, объём тела, объём документа) — 26 %, карта
элементов (`computeSignature`) — 7 %, решение эскизов окружностей — 5 %.

Изменено (`docs/modeling/PART_DOCUMENT.md`, «Инкрементальное перестроение»): кэш фактов о
формах (валидность, объём, «готова к булевой операции» — результат `booleanOp` не проверяется
`BRepAlgoAPI_Check` второй раз), сигнатуры неизменных элементов берутся из входа, эскизы и
вспомогательная геометрия без ссылок не зависят от цепочки тела.

Профиль после: `kernel::booleanOp` — 86 %, из них проверки ядра (`judge`: `BRepCheck_Analyzer`
и масса результата до и после `SimplifyResult`, масса аргумента) — 62 %; карта элементов — 4 %.
Дальнейший выигрыш — в ядре (один `judge`, параллельный `BRepCheck_Analyzer`, масса аргумента
без пересчёта), передано инженеру ядра. Сделано 2026-11-12 (`docs/kernel/GEOMETRY_HEALING.md`, раздел 2): одна
проверка результата на принятую попытку (сначала упрощённый, неупрощённый — только если тот
отвергнут), объём и площадь входов — только при `checkVolumeBounds` и с возможностью передать
известные (`BooleanOptions::argumentMass`, `BooleanResult::mass`), площадь результата — только
для границ объёма. Замер — раздел 5.

### Пересечения сборки из 300 компонентов (`assembly_300`)

Профиль до (34 выборки): `massOf` всей плиты с 299 отверстиями внутри `kernel::booleanOp`
(объём и площадь аргументов для проверки границ объёма) — 50 %, `BRepExtrema_DistShapeShape`
по всем граням плиты — 21 %, сама булева операция `Common` — 26 %.

Изменено (`docs/assembly/ASSEMBLY_DOCUMENT.md`, раздел 6): отбор по габаритам граней с
классификацией точки для деталей с далёкими границами; крупная деталь один раз разрезается
сеткой (`BRepAlgoAPI_Splitter`, плита — на куски по ≈ 4 грани), пара считается по кускам рядом
с другой деталью (`Common` и многопоточное расстояние). Первый вариант — обрезка плиты
габаритом каждой пары (`Common` с коробкой) — дал только 58 → 37 с: построение тел
(`BuildSplitSolids`) по всем 900 граням на каждую пару; отвергнут. Совпадение с прямым расчётом
по целым деталям проверяет `LocalAlgorithmMatchesWholeShapeReference`.

| Шаг | До, с | После, с | Порог, с |
|---|---:|---:|---:|
| пересечения: 44 850 пар → 299 кандидатов (299 касаний) | 58,4–73,8 | 7,5 | 25 |

Остальные шаги `assembly_300`, `step_large`, `hlr_1000_faces` не менялись (прогон
2026-11-12: 0,27 / 2,9 / 1,0 / 0,03 / 0,11 / 1,3 с для `assembly_300`).

### Прежние наблюдения, не изменённые фазой

1. **Крупный STEP:** импорт ~22 с на 65 МиБ / 5549 тел (≈ 3 МиБ/с), пик памяти ≈ 10 × размер файла. Файл
   100 МБ (цель плана фазы 5) потребует ≈ 1 ГиБ — для WASM (2–4 ГиБ) это предел, что
   подтверждает риск «Память WASM» плана.
2. **HLR 1000 граней:** точный вид сверху — 0,11 с; изометрия с выбором алгоритма — 5,5–7 с
   (кандидат на фоновый расчёт в Web Worker, `docs/ui/APP_SHELL.md`).

## 4. Как запускать

```bash
cmake --build build-occt --target test_stress_part test_stress_assembly test_stress_step \
  test_stress_hlr generate_corpus
ctest --test-dir build-occt -L stress --output-on-failure        # последовательно
cat build-occt/stress-report.jsonl
# крупный STEP другого размера:
cmake build-occt -DBENDCORE_STRESS_STEP_MB=110 && ctest --test-dir build-occt -R stress_step
```

Тесты входят и в полный `ctest`; в CI они идут отдельным последовательным шагом вместе с
`performance` и `offset_performance` (`docs/qa/QA.md`, раздел 4).
